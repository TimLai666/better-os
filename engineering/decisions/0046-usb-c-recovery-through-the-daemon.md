# ADR 0046: The USB-C recovery reloads one signed module and rebinds one controller, in helper units

## Status

Proposed on 2026-11-22 (ticket 101). Extends ADR 0029's helper-unit pattern,
as narrowed by ADR 0034's review, to two new hardware actions and one
after-sleep unit. ADR 0007's protocol, ADR 0029's attribute helper, and ADR
0034's LampArray helper are unchanged; `hardware::helper_sandbox()` is the
base of both new helpers.

## Context

On the owner's ASUS Vivobook S 14 M5406WA (BIOS M5406WA.314, kernel 7.0.0-42
and -43, Secure Boot on) two USB-C faults appear across suspend (ticket 101):

- The UCSI interface times out: `ucsi_acpi USBC000:00:
  ucsi_handle_connector_change: GET_CONNECTOR_STATUS failed (-110)` (every
  boot of this machine kept in its journal shows it about 20–36 s after
  boot) and, about ten seconds after a resume, `failed to re-enable
  notifications (-110)`, and a port stops charging. Reloading `ucsi_acpi`
  brings both ports back until the next suspend (the M5506WA report on
  linux-usb, 2026-06-23).
- The xHCI host for one USB-C side, `0000:63:00.4` (AMD 1022:151e), dies on
  resume: `AMD-Vi: Event logged [IO_PAGE_FAULT domain=0x0014 address=0x0]`,
  `WARN: xHC restore state timeout`, `PCI post-resume error -110!`, `HC died;
  cleaning up`. The hub work that disconnects its devices then waits for
  ever in `xhci_configure_endpoint` (the hung-task trace of the boot of
  2026-11-16 runs `hub_event` → `hub_quiesce` → `usb_disconnect` →
  `usb_disable_device` → `usb_hcd_alloc_bandwidth` → `xhci_check_bandwidth`
  → `xhci_configure_endpoint` → `wait_for_completion`), so every later
  suspend fails with `Freezing remaining freezable tasks failed … wq_busy=1`
  naming `workqueue usb_hub_wq` and `in-flight: …:hub_event`. 88 failed
  freezes in that boot, 1,672 suspend attempts in the night of 2026-11-13.

The owner decided on 2026-11-21: Secure Boot stays on and no Machine Owner
Key is enrolled, so the recovery must do the whole job with what the running
kernel already has, and ticket 101's out-of-tree module is withdrawn.

Both actions need root: unloading and loading a module, and writing a PCI
driver's `unbind` and `bind`. The daemon cannot do either itself: its unit
keeps `ProtectKernelModules=yes` (which removes `CAP_SYS_MODULE`, filters
the module system calls, and hides `/lib/modules`) and `BindReadOnlyPaths=/sys`
(ADR 0029).

### Why reloading the in-tree module is allowed under Secure Boot

Under Secure Boot Ubuntu's kernel locks itself down (`CONFIG_LOCK_DOWN_IN_
SECURE_BOOT=y`); this machine reads `none [integrity] confidentiality` in
`/sys/kernel/security/lockdown`. Lockdown does not forbid loading modules:
`kernel_lockdown(7)` (manpages 6.7, on this machine) says "Only validly
signed modules may be loaded". The rule is in `module_sig_check()`,
`kernel/module/signing.c` (read on torvalds/linux `master`, 2026-11-22): a
module whose signature `mod_verify_sig()` accepts sets `info->sig_ok` and
returns 0; only an unsigned module, one with unsupported crypto, or one with
an unknown key reaches `return security_locked_down(LOCKDOWN_MODULE_
SIGNATURE)`, and any other signature failure is refused even without
lockdown. `modinfo ucsi_acpi` on this machine: `intree: Y`, `signer: Build
time autogenerated kernel key`, `sig_hashalgo: sha512`, file
`/lib/modules/7.0.0-43-generic/kernel/drivers/usb/typec/ucsi/ucsi_acpi.ko.zst`.
That key is in the kernel's built-in keyring, so the distribution's own file
loads under lockdown, and nothing else does. Unloading (`delete_module(2)`)
and writing a driver's `bind` and `unbind` are not lockdown reasons (the
PCI restriction is on BAR access and config space, `kernel_lockdown(7)`).

## Decision

- **`org.betteros.UsbRecovery1`** on the daemon, served beside `Hardware1`:
  - `Findings() → s`: this boot's kernel log classified by
    `hardware_core::usb_recovery::classify` (`UsbFindings`: counts, the dead
    controller's PCI address, whether the hub work is hung, the run of
    failed sleeps). Never a line of the log. Ungated, like `GetStatus`;
    callers share one read for five seconds, and past eight waiting a call
    is busy. It exists for an account that cannot read the system journal
    (not in `adm` or `systemd-journal`); everyone else's Fixes page reads it
    with their own `journalctl`.
  - `ReloadUcsi() → s` behind `org.betteros.manager.usb-c-reload`
    (`allow_active=yes`, `auth_admin` otherwise). No argument. Refused as
    `usb_not_affected` off the model list and as `usb_nothing_to_reset`
    unless a timeout came after the last verified reload.
  - `RebindController() → s` behind
    `org.betteros.manager.usb-controller-rebind` (the same defaults). No
    argument: the daemon takes the address from this boot's last `HC died`
    line not followed by a verified rebind, and acts only when sysfs shows
    that function with class 0x0c0330, vendor and device on the list
    (1022:151e), and `xhci_hcd` bound. Refused as `usb_restart_needed` when
    the hub work is stuck: logged (the worker a hung-task report names:
    `INFO: task … blocked for more than …`, its own taint, "echo 0", and
    `task:` lines, then `Workqueue: usb_hub_wq`, the line that ends the
    report; any other line ends it first, and the query's `--grep` keeps
    the report's `task:` and `Workqueue:` lines and the first lines of
    every other dump, `WARNING:`, the cut-here line, `BUG:`, `Oops`, so a
    later dump's `Workqueue:` line never reads as the report's; or a
    failed freeze listing `usb_hub_wq`), or seen now (a
    worker named `kworker/…+usb_hub_wq` in state D in two looks two seconds
    apart; the kernel names a worker `+WQ` while it runs a work item of
    `WQ`, `wq_worker_comm()` in `kernel/workqueue.c`). Unbinding then would
    block behind that work for good.
  - `SetChoice(s choice, b on) → s` behind
    `org.betteros.manager.usb-recovery-settings` (`auth_admin_keep` for the
    active session): `ucsi-automatic`, `controller-automatic`,
    `power-off-when-sleep-blocked`, kept in
    `/var/lib/better-os/usb-recovery.json` (0644, written whole and synced),
    deleted when nothing is on. Power-off needs `controller-automatic`.
- **The reload helper** (`--reload-ucsi`, no argument) runs in a transient
  unit `better-os-ucsi-reload` (a fixed name: two reloads never run at once,
  whoever asked). It first finds and opens
  `/lib/modules/$(uname -r)/kernel/drivers/usb/typec/ucsi/
  ucsi_acpi.ko{.zst,.xz,.gz,}` with `O_NOFOLLOW` and checks it is a regular
  file owned by root and writable by nobody else, and, for a compressed one,
  that the kernel decompresses that format itself
  (`MODULE_INIT_COMPRESSED_FILE`, Linux 5.17): the kernel's own
  `/sys/module/compression` when it has one, bound read-only into the unit
  (`BindReadOnlyPaths=-…`), else `/boot/config-$(uname -r)` with
  `CONFIG_MODULE_DECOMPRESS=y` and the matching `CONFIG_MODULE_COMPRESS_*`.
  `/sys/module/compression` is `kernel/module/decompress.c`'s
  `compression_show`, which prints `MODULE_COMPRESSION` (`gzip`, `xz`, or
  `zstd`); that file is built only with `CONFIG_MODULE_DECOMPRESS`
  (`obj-$(CONFIG_MODULE_DECOMPRESS) += decompress.o`,
  `kernel/module/Makefile`; both read on torvalds/linux `master`,
  2026-11-22), so it exists exactly when the kernel can, and names the
  format; this machine reads `zstd`. Before the reload the daemon asks for the same
  check in a unit of the helper's kind (`--check-ucsi`, which unloads and
  loads nothing): the daemon's own unit has `ProtectKernelModules=yes`,
  which hides `/usr/lib/modules`, so a check made in the daemon itself
  refuses every reload (as 0.2.17 did on the owner's machine). A no is
  refused as `usb_module_cannot_load`, which the Fixes page says in words. Only then does it call `delete_module("ucsi_acpi", O_NONBLOCK)`
  and `finit_module(2)` on the open file, twice if the first load fails;
  any check that fails leaves the loaded module alone. The kernel checks
  the signature. Its unit is `helper_sandbox()` with
  `ProtectKernelModules=` left out, `SystemCallFilter=@module` added beside
  `@system-service`, `CapabilityBoundingSet=CAP_SYS_MODULE`, an empty
  read-only `/sys`, and `RuntimeMaxSec=30s` (an interface that is stuck can
  hold an unload for its own command timeout).
- **The rebind helper** (`--rebind-xhci ADDRESS`) runs in
  `better-os-xhci-rebind`. The address is the daemon's, parsed as exactly
  `dddd:bb:dd.f`. Its `/sys` holds only `/sys/bus/pci/drivers/xhci_hcd/
  unbind` and `bind` (writable) and the function's `vendor`, `device`, and
  `class` (read-only); it checks those again, writes the address to
  `unbind` (an unbound function is left so) and to `bind`. No capability.
  `RuntimeMaxSec=30s`.
- **After each:** the daemon looks again for up to 10 s (reload) or 15 s
  (rebind): both Type-C ports of the model (`/sys/class/typec/portN`) and a
  USB-C supply `online` when the mains adapter says a charger is plugged
  in; or `xhci_hcd` bound with root hubs under the function. Only
  directory entries and links are read under the controller: on a host
  whose hub work hangs, reading a USB device's attribute blocks (ticket 101
  saw `usb1/product` do it). The answer says what came back and what did
  not. A recovery that restored everything it checks (`Restored::complete`:
  for a reload, both ports and a plugged-in charger shown; for a rebind,
  the driver bound with root hubs) writes a marker line to the daemon's
  journal (`usb-recovery: ucsi_acpi reloaded`, `usb-recovery: controller
  rebound ADDRESS`); one that did not leaves the fault failing, to be tried
  again. The kernel log query (`_TRANSPORT=kernel` or `_UID=0
  SYSLOG_IDENTIFIER=better-manager-daemon`, as JSON with each entry's
  `_TRANSPORT`) reads every line the kernel wrote and, from the daemon's
  stream, only the two exact marker forms, so "failing now" means a fault
  after the last verified recovery and no other line from that stream is
  read as a fault or a sleep.
- **The sleep hook.** The daemon package ships
  `/usr/lib/systemd/system-sleep/better-os-usb-recovery`, one line:
  `exec /usr/libexec/better-manager-daemon --after-sleep "$1" "$2"`. The
  program checks both arguments against systemd-sleep's own, reads the
  choice file, and with nothing on returns at once. Otherwise it queues
  `systemd-run --no-block --unit=better-os-usb-after-sleep`, ordered after
  the four sleep services, so the run starts once the attempt is over and
  never holds a resume or fails a sleep; a run already queued is the run.
  systemd 255 reads hooks only from `/usr/lib/systemd/system-sleep`, which is
  dpkg's, so the file ships with the package and does nothing until the
  person turns a fix on; Undo turns the choice off, and removal deletes the
  file with the package and the choices (`--release-hardware`, postrm).
- **The after-sleep run** (`--usb-after-sleep`): with `ucsi-automatic`, it
  watches up to 25 s for the timeout the kernel writes after a resume and
  then makes the same reload; with `controller-automatic`, the same rebind
  of a dead controller, and the overnight guard. Its unit: `ProtectSystem=
  strict` with only `/run/better-os` writable, `ProtectHome=read-only`,
  `ProtectKernelModules=`, `ProtectKernelTunables=`, `ProtectKernelLogs=`
  (it reads the journal, not `/dev/kmsg`), `ProtectControlGroups=`,
  `NoNewPrivileges=`, no network (`IPAddressDeny=any`, `AF_UNIX` only),
  `SystemCallFilter=@system-service`, `CapabilityBoundingSet=CAP_SETUID
  CAP_SETGID`, and `RuntimeMaxSec=120s`. It reaches the helpers through
  systemd-run like the daemon does, so their sandboxes are the same.
- **The overnight guard** (`hardware_core::usb_recovery::guard`): once two
  sleep attempts in a row failed because `usb_hub_wq` would not freeze, the
  run notifies every person with an active local graphical session, once
  per run of failures (kept in `/run/better-os/usb-recovery.json` before
  anything is sent; a run that cannot keep it tells nobody). The
  notification is sent as that person: the program starts itself with
  `--notify-sleep-blocked zh-TW|en` under their uid and primary group, no
  supplementary group, an empty environment but
  `DBUS_SESSION_BUS_ADDRESS=unix:path=/run/user/UID/bus`, its standard
  input, output, and error on `/dev/null` (so no process of the person's
  holds the unit's journal stream, whose markers the recovery trusts), in
  the language AccountsService (else `/etc/default/locale`) names, by the
  one rule every Better OS notification follows (`better_core::locale`:
  `zh_TW`, `zh_HK`, `zh_Hant` are Traditional Chinese). The call has a
  five-second timeout and the child ten seconds, then it is ended. It
  powers off through logind's `PowerOff(false)` only when the person chose
  it, logind says the lid is closed (`LidClosed`; not knowing is not
  closed) and the laptop is not docked (`Docked`: a dock or an external
  screen may mean it is in use with the lid shut; not knowing is docked),
  no `block` inhibitor holds `shutdown` (an upgrade, a burn; not knowing
  counts as held), Better Manager's privileged service is not in a
  transaction (`/run/better-os/daemon-busy`, which exists exactly while one
  runs; whether apt itself holds a logind inhibitor while dpkg runs is not
  known, so the marker is checked regardless), no other login session
  exists, whatever its uid (the same person over SSH or on a tty may be
  running work; a session that cannot be read, or of a class this build
  does not know, counts as one), and no account lingers (logind's
  `ListUsers`: `Linger` set, or `State` `lingering`, a user manager running
  with no session; an account that cannot be read counts as lingering).
  The login classes are systemd's `session_class_table`
  (`src/login/logind-session.c`, meanings in `logind-session.h`, read on
  `main` on 2026-11-22): `user`, `user-early`, `user-incomplete`,
  `user-light`, and `user-early-light` are a person's login; `greeter`,
  `lock-screen`, `background`, `background-light`, `manager`,
  `manager-early`, and `none` are not; the systemd of 22.04 (249) and 24.04
  (255) has a subset of that table. Everything the power-off depends on
  is read again right before it, after the notifications (which can take
  ten seconds a person); a world that changed meanwhile stops it, and the
  run may still power off later in the same run of failures. At most once
  per run of failures. The default, once the fix is on, is notify only.

## Why these are acceptable

- **A signed in-tree module, by a fixed name.** Nothing the caller sends
  names a module or a file. The file is the distribution's, under the
  running kernel's own directory, refused when it is a link or anyone but
  root can write it, and the kernel itself refuses it unless its signature
  checks out. The worst a reload does is what the person's own `modprobe -r
  ucsi_acpi && modprobe ucsi_acpi` does: the Type-C ports' Linux-side state
  is rebuilt, and a USB-C display or dock in an alternate mode may
  renegotiate. The daemon refuses it while the interface is working.
- **One PCI function, chosen by the daemon.** The address comes from this
  boot's kernel log and is checked against sysfs and the list before the
  helper starts, and again inside it. It is never free text. A controller
  the kernel already declared dead has no working device on it, so its
  rebind loses nothing that was not already lost; the daemon refuses while
  the hub work is stuck, where an unbind would block in the kernel for
  good.

## What a hostile local process can make root do

- **At the desk** (the active local session, `allow_active=yes`): call
  `ReloadUcsi` and `RebindController`. Each runs only when this boot's log
  shows the fault after the last verified recovery, and at most one helper
  run of each kind every 30 s (reload) or 60 s (rebind), succeeded or
  failed: a call inside the cooldown gets that run's answer back
  (`recent`, or the same failure) and starts no helper; one at a time (an
  async lock, no thread per caller; and systemd refuses a second unit of
  the same name, `Busy`, which is never kept). A refusal is decided afresh
  each time, from findings at most five seconds old shared with
  `Findings`, so a fault that appears just after a refused call is repaired
  by the next one and a caller in a loop reads the journal at most once in
  five seconds. So: reload a driver that has stopped answering, twice a
  minute at most; rebind a dead controller once a minute at most.
- **To change a choice** an administrator authenticates
  (`auth_admin_keep`): a hostile process cannot turn the power-off on.
- **Inactive or remote sessions** authenticate for everything.
- **The sleep hook** runs as root from `systemd-sleep` with arguments from
  systemd only; with nothing chosen it reads one file and returns.
- **A forged line** in the daemon's stream would make the page and the
  after-sleep run believe a recovery, a controller death, or a run of
  failed sleeps happened. Markers are read only from root's (`_UID=0`)
  `better-manager-daemon` stream, and from it only the two exact marker
  forms; every fault and sleep line must carry `_TRANSPORT=kernel`, which
  only the kernel's log gives. The one child of the person's the run
  starts, the notification, gets `/dev/null` for its output, so no
  process of theirs holds a descriptor of that stream (an independent
  review on 2026-11-22 found it did, and that on a machine with
  `kernel.yama.ptrace_scope=0` the person could have written trusted lines
  through it).
- **A compromised reload helper** holds `CAP_SYS_MODULE` and nothing else,
  with no writable file system, no network, an empty `/sys`, a read-only
  `/proc/sys`, a private `/dev`, a system-call allow-list, and 30 s. Under
  lockdown it can load only modules the kernel's keys signed (any of the
  distribution's) and unload any module that is not in use. That is the
  power the helper exists for, bounded by Secure Boot; its input is
  nothing but the running kernel's release.
- **A compromised rebind helper** can write any address to `xhci_hcd`'s
  `unbind` and `bind`, which can take another USB controller off its driver
  until the next bind or boot. It has no capability, sees no other sysfs
  file, and its only input is the daemon's validated address.

## Not chosen

- **`modprobe -r ucsi_acpi` and `modprobe ucsi_acpi`** (the draft of
  2026-11-13): kmod reads `/sys/module` to decide what is loaded, so the
  helper's `/sys` could not be empty, `-r` also removes unused dependencies
  (`typec_ucsi`), and `/etc/modprobe.d` may hold `install` commands that run
  a shell as root. The two system calls need none of it.
- **The reload in the daemon's own unit**, with `ProtectKernelModules=`
  removed (the draft): every dpkg maintainer script the daemon runs would
  then inherit module loading.
- **A PCI remove and rescan of the function**: `rescan` walks every bus and
  would need `/sys/bus/pci/rescan`; unbind and bind touch one function.
- **A hook that carries logic, or loads the module itself**: refused by the
  ticket; the hook is one `exec`.
- **Powering off without the person's choice, or with the lid open**: work
  in open applications would be lost without anyone having chosen it.
- **A DKMS module with a quirk** (ticket 101's part 2): needs a Machine
  Owner Key under Secure Boot, which the owner declined on 2026-11-21. Only
  the upstream report remains.

## Consequences

- Offering another machine or controller is a line in
  `crates/hardware-core/data/usb-recovery-machines.txt` for a fault someone
  reproduced on it, with this record's reasoning unchanged; another kind of
  action is a new record.
- **What a real system manager checks, and what it does not:** CI runs
  `packaging/hardware-unit/check.sh` in a throwaway container with systemd
  255 as PID 1: the reload helper's unit starts with its properties, sees an
  empty `/sys`, a readable `/usr/lib/modules`, a read-only `/proc/sys`, and
  `CapBnd` 0x10000 (`CAP_SYS_MODULE` only), and the helper starts in it;
  the rebind helper's unit sees one entry under `/sys`, exactly the
  driver's two files, cannot change the function's identity, has no
  capability, and the real helper rebinds a stand-in function (tmpfs over
  `/sys/bus/pci` first) and refuses one of another kind; the after-sleep
  unit starts, writes `/run/better-os` and not `/etc` or `/var`, with
  `CAP_SETUID CAP_SETGID` only; the hook queues nothing while nothing is
  chosen; removal forgets the choices. **Not verified:** a container shares
  the host's kernel, so no module system call is ever made there (it would
  unload the CI host's module), and no real controller is unbound; no
  `finit_module` has run through the sandbox, and whether
  `SystemCallFilter=@module` with `@system-service` admits it is read from
  systemd's documentation, not seen. The notification as the person (with its timeouts), the
  logind calls (`Docked` included), and the post hook after a *failed* attempt (read from
  systemd 255's `src/sleep/sleep.c`; the hook also queues the run from its
  `pre` call, so the run happens either way) have run only against fakes.
  Until CI has run the check once, even the container part is unobserved:
  nothing on the development machine can run it (no Docker daemon).
- Ticket 101's "measured on the owner's machine before and after" needs the
  next release installed and a real occurrence; the ticket stays open with
  that left.
